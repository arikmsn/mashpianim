# Tests

## Unit tests (no services required)

```
npm test
```

Runs `tests/**/*.test.ts` with Node's built-in runner (`node --test`, TypeScript via `--experimental-strip-types`, Node ≥ 22.6). No extra dependencies.

`authz.test.ts` covers the pure authorization rules used by the API routes: registration role whitelist, profile field allowlists, connection participation, public product projection, dev-login availability.

`match-errors.test.ts` covers the mapping of `match_connection()` database errors (`NO_CREDITS`, `CONNECTION_NOT_PENDING`, …) to API responses and the Postgres unique-violation detection used for duplicate hearts.

`uploads-products.test.ts` covers the storage-path ownership checks behind `save-portfolio` / `save-connection` / video delete, the connection statuses that accept a deliverable, and the product update allowlist (no `category` column).

`client-cache.test.ts` covers the per-user ownership of the SWR cache (`syncCacheOwner`): a different user, or a logout, drops the previous user's cached API responses.

`chat.test.ts` covers the chat card guards (`isBriefSnapshot` / `isVideoCard`), the texts the app writes in a person's name, the 24 h final review window and the regions list; `notification-links.test.ts` pins which notification types open the chat.

`rate-limit.test.ts` covers client IP extraction, limiter key normalisation and the retry message. `uploads.test.ts` covers the video pre-flight (type + 150 MB cap), image magic-byte sniffing, Storage error mapping and the admin timeline settings parser. `credits.test.ts` covers the credits state until online payment exists (fresh / empty / last / ok), the card hint and the owner's contact notice. `onboarding.test.ts` covers the walkthrough flags (first ending wins, skip = seen, normalisation), the welcome rules (creators only, after the terms gate, once), matched statuses and the card / moment copy. `otp-channel.test.ts` covers the login-code channel (env default, the client's choice, the one-segment SMS text without links, E.164). `messaging-switch.test.ts` covers the WhatsApp notifications switch (off unless exactly `on`). `admin-creators.test.ts` / `admin-connections.test.ts` cover the admin aggregations, labels, null-safe search and list filters; `viewer-admin-flag.test.ts` the `is_admin` roles. `chat-block.test.ts` covers the chat stop (owner's sentence, `isChatBlocked`, the contact-form subject, the notification types) and `detectContactInfo` agreeing with the send-time filter; `admin-connections.test.ts` also covers the transcript sides and the contact-sharing warnings (clean chat talk raises nothing; spaced / dictated numbers, channel names, off-platform phrasing, spelled-out addresses and bare domains are flagged; Hebrew words are bounded). `feedback.test.ts` also covers the thread helpers (reply validation, where a reply moves the status, thread assembly with the legacy note, the "migration 020 not applied" answers); `notification-links.test.ts` the `feedback_reply` / `feedback_updated` deep link to `/profile?feedback=<id>`. `payments.test.ts` covers the SUMIT purchase helpers: prices from the admin settings, the offers and the best per-video price, the `SUMIT_PAYMENTS` switch, invoice-detail validation, the exact beginredirect body, the response envelope, payment verification (valid / ILS / amount / order), the return-URL parameters and the landing texts. `roles.test.ts` covers the second-role registration mode (new / complete / add_role) and that an account with both profiles holds both roles. `digests.test.ts` covers the WhatsApp digests (the switch, the 18:00 / Sunday 10:00 windows in Israel time, each heart announced once, the creator and business texts, when a business summary is worth sending) and the message-log counts (today / week / month per channel in Israel days, failures apart, dry runs ignored, the daily series). `billing-content.test.ts` covers the billing page copy (defaults, overrides and the blank-to-hide referral rule, the {placeholders}, the "ש: / ת:" FAQ parser, bullets) and the first-purchase discount (the setting, the discounted offers with the original price kept, the SUMIT item name, savings against single videos).

## Database-level checks (Batch 2: migrations 007/008)

These hit Supabase directly with the publishable (anon) key, which is what an attacker who extracts it from the browser would do. `URL` = `NEXT_PUBLIC_SUPABASE_URL`, `ANON` = `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `JWT` = a signed-in user's access token (from the `sb-*-auth-token` cookie, base64 JSON → `access_token`).

| # | Check | Request | Expected |
|---|---|---|---|
| 14 | Signed-in user cannot write any table | `PATCH $URL/rest/v1/users?id=eq.<own id>` with `apikey: $ANON`, `Authorization: Bearer $JWT`, body `{"type":"admin"}`; repeat for `connections`, `messages`, `notifications`, `brand_profiles`, `products`, `videos` (INSERT/UPDATE/DELETE) | 403 `42501 permission denied for table …`; rows unchanged |
| 15 | Anonymous cannot write | `POST $URL/rest/v1/users` with only `apikey: $ANON` | 401 `42501` |

| 17 | Reads still scoped (Realtime depends on this) | `GET $URL/rest/v1/connections?select=id,status` with a user JWT; same with anon key only | own rows only; anon gets `[]` |
